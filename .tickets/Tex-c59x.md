# ホームの配置範囲が伸びる、編集開始時の大きさ、一覧のスクロールバーの余白

実機での指摘（2026-11-22）:
- 画面の一番下にアプリを置くと配置できる範囲が伸びていき、どんどん縦長にできる。配置できる範囲の大きさは Launcher3 と同じ計算にしたい（行数は画面の高さを行の高さで割って切り捨て？）
- 編集に入るとき、一瞬キーボードが出ているときの大きさのプレビューが挟まる。最初からキーボードを下ろした状態の大きさにしたい
- 全アプリ一覧のスクロールバーの位置が少し変で、上に謎の余白がある

## Acceptance Criteria

- [x] 一番下に置いても配置できる範囲が伸びない
- [x] 範囲はキーボードを下ろした状態のホームの1ページ分で、行数は入るだけ
- [x] 編集に入った最初のフレームから、キーボードを下ろした状態の大きさになる
- [x] 一覧のスクロールバーが一覧の上端から始まる

## 結果（2026-11-22）

- 範囲が伸びる原因: グリッドの行数を「使っている行 + 編集中の余白の行」と「見えている高さ」から毎回決めていた。一番下に置くと使っている行が増え、次の編集でさらに余白が足されていた
- 範囲: Launcher3 のページと同じく、ステータスバーの下から検索フィールド（ホットシート）の上まで、キーボードを下ろした状態の高さ（LauncherRootLayout が測るときに HomeGridView.pageHeight に渡す）。行数は入るだけ（高さ ÷ アイコンと余白の高さ、切り捨て）、セルの高さは Launcher3 と同じく高さ ÷ 行数。Launcher3 は numRows をグリッドの設定から取るが、アプリ名のないこのランチャーではセルが間延びするので、入るだけの行数にした。以前の版で範囲の外に置いたアイテムがあれば、そこまで広げる（消さない）
- 編集開始: LauncherRootLayout.isEditLayout の間は、ホームの表示範囲をキーボードを下ろした状態の高さにすぐ合わせる。縮小の計算もキーボードを下ろした状態のフィールドの位置で行う。編集が終わって縮小が戻りきったら解除する
- スクロールバー: AllAppsRecyclerView.getScrollBarTop が上流のヘッダーの分（all_apps_header_top_padding 36dp）を返し、レイアウトにもヘッダーの下の余白（14dp）があった。このランチャーの一覧の上にヘッダーはないので、どちらもなくした
- エミュレータで確認: 編集に入った直後（キーボードが下りている途中）から縮小後の大きさになる。一番下より下では落とし先がない。スクロールバーが一覧の上端から始まる
