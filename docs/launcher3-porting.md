# Launcher3 porting policy

## Approach

For Android users, the basic feel of a launcher is how AOSP Launcher3 behaves. So, **for anything that affects the feel, we copy Launcher3's implementation as much as we can**.

- We do not fork and modify Launcher3. The structure of this launcher's home screen (vertical scrolling, an always-on keyboard, the all apps list under the keyboard) differs from the core of Launcher3
- We copy only the parts we need, source and all. Dependencies on other parts of Launcher3 are absorbed by small stand-in classes that we provide
- So that we can keep up with Launcher3 updates, imported code keeps its original form as much as possible

---

## Baseline versions

| Repository | Baseline |
|---|---|
| `platform/packages/apps/Launcher3` | Tag `android-17.0.0_r1` |
| `platform/frameworks/libs/systemui` (`iconloaderlib` and others) | Tag `android-17.0.0_r1` |
| `platform/packages/modules/IntentResolver` (share sheet) | Tag `android-17.0.0_r1` |

- We do not use the main branch. main has unreleased features behind flags, so it does not match the behavior of release builds
- When a new release tag comes out, follow it with the [update procedure](#update-procedure)

### What we write ourselves

Mostly behavior unique to this launcher, where importing has little benefit. For the components listed under "What we use as reference" above, we also write the code ourselves.

- The search field, the always-on keyboard, and handling of back
- Search (normalization, matching, ranking, learning)

- The container for the vertically scrolling home screen (reordering the cells inside uses Launcher3's logic)
- Saving data

The app's home screen classes are split to match the Launcher3 classes whose roles they take on, and each file's description names the corresponding class (`HomeController` gathers the role of Launcher, `HomeActivityContext` is the Launcher itself and extends the Launcher compat class, `HomeLoader` (LoaderTask and others), `HomeItemInflater` (ItemInflater and ItemClickHandler), `HomeSystemShortcuts` (Launcher.getSupportedShortcuts), `HomeWorkspace` (extends the Workspace compat class), `HomeScrollView` (vertical scrolling of the page)). Search results live in `SearchResults` (the search part of ActivityAllAppsContainerView).

The home Activity (`LauncherActivity`) extends the framework `Activity`, like Launcher3's `BaseActivity`, and does not use AppCompat or Material Components. The theme inherits from `Theme.DeviceDefault.DayNight`, like `BaseLauncherTheme`. Dialogs are `android.app.AlertDialog`, and colors come from `materialColor*` in dynamiccolors (the system colors). The lifecycle and saved state that Compose (the widget resize frame) needs are held with `LifecycleHelper`, like `BaseActivity`. Back is received with `OnBackInvokedDispatcher`, like `registerBackDispatcher`. The reason is that AppCompat's View substitution (`TextView` to `MaterialTextView`) also affects how widget RemoteViews are shown, and breaks them (Tex-uus1). constraintlayout pulls in AppCompat transitively, as in Launcher3, but we do not use it.

The home Activity is not a copy of upstream `Launcher.java` (a subclass of `StatefulActivity`) (decided on 2026-11-25, Tex-zwo5). The parts of upstream `Launcher` that matter for this launcher (drag, accessibility, popups, adding and binding items, the widget add flow) go into the compat `Launcher` (`compat/launcher3-internal`), which is not an Activity, as `derived=` sections in upstream order, and `HomeActivityContext` extends it. What stays in the Activity is the lifecycle wiring and the handling of the search field, the always-on keyboard and search results, which upstream does not have. The reasons are as follows.

- Most of the rest of `Launcher.java` (2,903 lines) is wiring for the Activity lifecycle (Dagger's `LauncherComponent`, overlays, Quickstep hooks, rotation, pages, the hotseat). A copy would be mostly removal markers, and the cost of applying upstream updates would outweigh the benefit of matching upstream
- Upstream makes `DragLayer` the root and handles the keyboard through insets. In this launcher, `LauncherRootLayout` takes care of "the drag layer extends to the top of the keyboard". The layout during the keyboard show and hide animation is a foundation of this launcher, and rebuilding it is risky
- It would reverse the current ownership, where `HomeController` creates `Launcher`, move code from Kotlin to Java, and change configuration changes from `recreate()` to `onIdpChanged`. Drag and loading races that we have fixed could come back
- What we would gain (the compat `addEventCallback`, `LauncherTracker` and `LauncherContextWrapper` go away; predictive back) is small. The all apps list, which needs predictive back, gets it with `AllAppsTransitionController.onBackProgressed` (Tex-ojza)

- Imported code goes in `third_party/` and is not mixed with our own code

  - The tag it is based on
  - Whether we changed it
- In Gradle, everything under `third_party/` builds as library modules

## Rules for making changes

- Avoid editing imported files directly as much as possible
- Dependencies on other parts of Launcher3 (`Launcher`, `DeviceProfile`, `LauncherPrefs`, feature flags and so on) are absorbed by stand-in classes (the compat layer) outside `third_party/`
- The compat layer uses the same package and class names, and implements only the parts that are used
- If an edit is truly needed, add a comment starting with `// CaretLauncher:` at that spot
- Compat classes that bring in upstream code are made by cutting the unused parts from the upstream file (`derived=` in `UPSTREAM.md`), so that updates can be 3-way merged
  - The parts we keep stay in upstream order and style (including line breaks and indentation). Do not reorder or rewrite them
  - Put a `CaretLauncher:` marker right where each change is (do not only summarize the changes in the class description)
  - Members that only CaretLauncher has go together under `// CaretLauncher: members CaretLauncher adds.` at the end of the class
  - Compat classes with only names and signatures are `ref=`, and we look only at the upstream diff
- Feature flags (`Flags.xxx()` and so on) are fixed to their values in the release of the baseline tag
  - For the values, refer to that release's config in AOSP `build/release` (`scripts/check-upstream.py` checks the `Flags` compat class against the `flag=` lines)
  - Anything we cannot confirm follows the behavior of a real Pixel device

## Update procedure

These are the steps for when a new release tag comes out.

1. Run `scripts/update-upstream.sh third_party/launcher3 <new tag>` (the same for `third_party/systemui`)
   - It 3-way merges the files listed in `path=` in `UPSTREAM.md` and the compat classes listed in `derived=` (made by cutting from upstream files) with `git merge-file` (ours = our side, base = the previous tag, theirs = the new tag). If upstream changed a part we cut, it shows up as a conflict, so decide whether to take the change (usually keeping it cut is fine; take it if the fix touches a part we use)
   - Files added upstream are copied. Files removed upstream are removed if we have not changed them (it also suggests where they may have moved)
   - Next, `scripts/check-upstream.py <dir> --to <new tag>` shows upstream changes in things the merge does not cover (below)
   - If there are conflicts or errors, the tag in `UPSTREAM.md` stays at the previous one. Fix them and run the same command again (leftover conflict markers also count as conflicts). The tag is rewritten only when everything passes
2. Review the upstream changes that `check-upstream.py` reported, and apply them here
   - Upstream diffs of `ref=` files (stand-in classes in the compat layer, code transcribed to the app side, `Android.bp` and build settings). For files in the same language, it shows only the parts related to lines that appear in our file
   - Additions, changes and removals of extracted resource values (`values_root=`)
   - Changes to feature flag values in the release (looked up from the release config in `release_config=`, following inheritance)
3. Add newly needed dependencies to the compat layer
4. Run `scripts/check-upstream.py <dir>` (without a tag) to confirm there are no mismatches with the new tag. It checks that the extracted values match upstream, that the feature flag values match the release, and that `ref=` files exist both upstream and here. For values changed on purpose, put a comment starting with `CaretLauncher:` right before the element
5. Pass the build and tests, and check the feel on the emulator and a real device
6. For the "Wallpaper & style" integration, check on a real Pixel device that the items appear and work

`check-upstream.py` makes a shallow clone of upstream and keeps it in `UPSTREAM_CACHE` (by default, `caretlauncher-upstream` in the temp directory). The meaning of the lines in an `UPSTREAM.md` block is described in each `UPSTREAM.md`.
